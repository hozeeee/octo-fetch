# 脚本分类与注入能力

## 已确认的行为
- **行动**：现有脚本，手动或经 MCP 触发，在已有 Puppeteer 会话中完成一次任务；任务内部可以包含多步操作和有界循环。本次不新增定时调度。
- **注入**：在 Puppeteer 运行时安装监听器、接口改写等逻辑，初始化结束后继续有效，直到标签关闭或网站停止；不是只能访问 `window/document` 的网页脚本。
- 注入支持修改请求 URL、请求头、请求体，以及服务器真实返回的 JSON／文本响应。
- 绑定、顺序、参数、启用状态及源码的修改均在网站重启后生效；当前会话及其后续新标签使用启动时的配置和源码快照。

## 脚本模型与兼容
修改 `src/shared/scripts.ts`、`src/main/scripts/store.ts`：
- 增加 `kind: 'action' | 'injection'`；缺失类型的旧本地脚本、旧 MCP 输入默认视为 `action`，保留原 ID、源码、参数、时间与日志。
- 两类共用名称、说明、适用域名、变量和源码。`timeout` 对行动表示总执行超时，对注入表示初始化超时；注入初始化完成后不受行动的总时长限制。
- 创建时选择类型。编辑时允许切换，但运行中或仍被网站绑定的脚本禁止切换类型；运行中的注入允许保存同类型新版本，提示重启后生效。
- 导出元数据升级到 v2，包含类型；导入兼容 v1 并默认行动。继续不导出本机 ID、参数实值、日志或登录态。
- 复用已有 `createdAt`、`updatedAt`：创建时同时赋值，编辑只更新修改时间；运行、保存上次参数和写日志不得修改它们。导入视为本机新建。

## 页面管理与绑定
修改 `src/shared/model.ts`、`src/renderer/src/features/sites/Sites.tsx` 及站点保存逻辑：
- 网站配置增加有序的 `injections: { scriptId, enabled, values }[]`，旧配置默认为空；同一脚本不得重复绑定。
- 页面编辑弹窗增加注入配置区：只可选择注入脚本，支持添加、移除、启停、上下调整顺序，并按脚本变量声明填写该网站专属参数。
- 保存时校验引用存在、类型正确、参数有效及适用域名；启动时再次校验，防止脚本修改后配置失效。错误明确指出脚本和原因，不静默忽略。
- 注入的 `match` 校验网站的配置网址，表示该网站是否适用；绑定后覆盖该网站实例的标签。具体接口通过拦截规则匹配，不把页面域名误当成 API 域名白名单。
- 页面列表展示绑定数量、运行中的注入状态和“待重启生效”。比较启动快照与当前配置／脚本版本，避免误报已生效。
- 被网站引用或仍在运行的注入禁止删除，并列出相关网站；先解绑并停止相关会话后才可删除，不做隐式级联删除。

## 常驻注入运行时
新增 `src/main/scripts/injections.ts`、`src/main/scripts/injection-worker.ts`，接入 `src/main/browser/manager.ts`、`src/main/index.ts` 和构建入口：
- 每个绑定了启用注入的网站使用一个常驻 Worker，连接该网站现有 Browser；按标签和脚本隔离执行上下文，按绑定顺序初始化。
- 保留 `page`、`browser`、`octo.site`、`octo.vars`、日志和等待能力，增加 `octo.onDispose(fn)` 注册清理函数。源码仍为支持 `await` 的异步函数体，初始化阶段只安装能力，不等待尚未导航的页面 DOM。
- 初始页和应用创建的标签在首次导航前等待注入就绪；以 `generation + targetId` 去重，避免重复安装。刷新不重复安装 Puppeteer 监听器；网页上下文初始化可通过 `page.evaluateOnNewDocument` 完成。
- 网页自行打开的弹窗在被管理器接管后安装注入；不承诺追溯接管前已经发生的首批请求，也不自动刷新弹窗。
- 标签关闭时清理该标签资源；网站停止、浏览器异常退出、启动失败和应用退出均终止相关上下文、监听器、CDP 会话及 Worker。清理有超时兜底，不关闭其他网站或清除登录态。
- 初始化失败或超时不继续首次导航，报告错误并清理本次启动。Worker 使用主进程监督和心跳，避免异步回调死循环拖住应用。
- 注入与行动使用独立活动状态：常驻注入不占用“每网站一个行动”的运行名额，原行动的运行、取消、超时与结果语义保持不变。

## 请求与真实响应改写
新增统一的拦截调度模块，替换 `BrowserManager.addPage` 中独立直接放行请求的逻辑：
- 每个受控页面只由一个平台 CDP Fetch 调度器处理网络改写，并保留现有非法导航协议拦截。脚本网络改写统一通过以下 API 注册，不混用原生 `setRequestInterception` 或独立 Fetch 处理器：
  - `octo.interceptRequest({ urlPattern }, handler)`：接收请求数据，返回 URL／method／headers／postData 的修改，或明确的阻止／模拟响应决定。
  - `octo.interceptResponse({ urlPattern }, handler)`：接收请求与原始响应数据，返回 status／headers／body 修改；返回空值表示不修改。
- Worker 保存回调；主进程调度器发送可序列化事件并接收修改决定，用户代码不在 Electron 主线程执行。
- 多脚本按绑定顺序串行处理，后续处理器看到前面修改后的数据；阻止或模拟响应为终结决定。同一暂停请求只完成一次，未匹配请求正常放行。
- 真实响应通过 `Fetch.getResponseBody` 读取、`Fetch.fulfillRequest` 回传，不额外重发 HTTP 请求，保持原请求登录态。响应头使用保留重复项的结构，确保 `Set-Cookie` 等不丢失；正文改写后修正长度与编码相关头。
- 首期正文改写覆盖普通 HTTP Fetch／XHR 的 UTF-8 JSON／文本，正文上限 5 MiB。HEAD、无正文状态、重定向、二进制、SSE／流式及 WebSocket 不做正文改写；明确跳过并按需记录原因。
- 每次拦截处理总预算 10 秒。处理器异常、超时或 Worker 故障时，该请求回退到原始放行，记录错误并停用本次会话中故障脚本的后续
