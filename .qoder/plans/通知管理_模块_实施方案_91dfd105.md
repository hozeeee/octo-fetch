# 通知管理模块实施方案

## 一、目标与首版范围
- 已确认渠道：钉钉群机器人、企业微信群机器人、飞书群机器人、SMTP 邮件、通用 HTTP Webhook。
- 核心原则：通知是附加操作，发送慢或失败均不改变脚本、注入和编排任务的执行结果。
- 行动脚本与注入脚本使用相同 API；注入仍须在页面管理中显式绑定，不改变现有生效规则。
- 首版统一提供「标题＋纯文本正文」，不做 Markdown 渲染、富文本卡片、附件和 @ 指定成员。
- 不做自动重试、持久化待发送队列、消息模板中心、通知分组，以及任务成功/失败自动触发规则。需要通知时由脚本显式调用。

## 二、模块界面与通道配置
侧栏新增「通知管理」，位于「任务编排」之后，包含「通知通道」「发送日志」两个页签。

### 通知通道
- 支持新建、编辑、启用/停用、删除、测试发送、复制调用示例；同一种渠道可以配置多份，例如不同钉钉群、不同邮件收件人。
- 通用字段：显示名称、唯一调用标识 `key`、渠道类型、启用状态、可选正文前缀。
- `key` 使用小写英文开头，允许数字、下划线和连字符，长度 2–64；创建后不可修改，显示名称可以修改。脚本只依赖 `key`，不依赖名称或本机 UUID。
- 列表显示名称、标识、类型、状态、最近一次发送时间和结果；不显示完整机器人地址或凭据。最多保存 100 个通道。
- 新建后默认启用，但保存本身不发送通知；测试按钮明确提示会向真实接收端发送测试消息。
- 测试使用已保存配置并走正式发送链路，结果在当前界面及发送日志中显示；停用通道不可测试。

| 渠道 | 配置与发送方式 |
| --- | --- |
| 钉钉机器人 | Webhook 地址、可选加签密钥；发送 text 消息。正文前缀可用于满足机器人关键词要求。 |
| 企业微信机器人 | Webhook 地址；发送 text 消息。 |
| 飞书机器人 | Webhook 地址、可选签名密钥；发送 text 消息。正文前缀可用于满足关键词要求。 |
| SMTP 邮件 | 主机、端口、TLS/STARTTLS、认证账号及密码/授权码、发件人、多个收件人及可选抄送；标题作为主题，正文作为纯文本。 |
| 通用 Webhook | URL、自定义 Header；固定 POST JSON，发送统一消息结构，HTTP 2xx 表示接口受理。 |

机器人正文组装为前缀、标题、正文，空项省略。无标题邮件默认主题为「Octo Fetch 通知」。机器人按各平台最终 UTF-8 字节限制校验，超限记录明确原因，不静默截断或拆成多条。

Webhook 请求体固定为 `{ id, title, content, createdAt, source: { kind, scriptId?, runId?, siteId?, tabId? } }`，不携带网站 Cookie、页面内容或 URL。首版不提供任意请求体模板、任意方法或脚本求值。

## 三、脚本调用设计
推荐入口是一个方法，不为不同平台分别暴露 API：

```javascript
// 单通道：后台发送，无需 await。
octo.notify('ops', {
  title: '采集完成',
  content: '本次新增 12 条数据'
});

// 简短通知。
octo.notify('ops', '发现需要处理的新订单');

// 多通道：各自独立发送，一个失败不影响另一个。
octo.notify(['ops', 'daily-mail'], {
  title: '每日汇总',
  content: '今日新增 128 条记录'
});

// 复用现有脚本变量切换接收端。
octo.notify(octo.vars.notificationChannel, '任务已完成');
```

接口契约：

```typescript
notify(
  target: string | string[],
  message: string | { title?: string; content: string }
): void;
```

- 方法同步提交通知，不返回 Promise，不等待网络或磁盘；正常通知错误在 API 内处理，不要求脚本编写 `try/catch`。
- 返回不代表发送成功。提交时生成关联 ID，在脚本日志记录提交信息，最终结果查询通知日志。
- 通道必须显式指定；数组去重，最多 10 个标识。没有隐式默认通道或默认群发。
- 标题最多 200 字符，正文最多 16 KiB UTF-8；平台存在更小限制时按平台限制处理。参数错误写脚本警告；通道不存在、已停用、发送失败等写独立通知日志。
- 收件人、Webhook 地址和密钥只能在通知管理中配置，不能通过脚本参数覆盖。
- 仅脚本运行环境提供 `octo.notify`，不会向 `page.evaluate` 的网页环境暴露通知能力或凭据。
- 编辑器增加参数提示；通知列表提供可复制示例。保留现有默认脚本模板的无通知行为，另提供通知示例，不让新建脚本默认对外发送。

## 四、后台发送与生命周期
### 实现结构
`脚本 Worker → 主进程通知服务 → 渠道适配器 → 外部接收端`

- 在两个 Worker 的 `octo` 上挂载薄代理，复用共享参数校验及消息格式。
- 主进程接收消息时立刻绑定真实运行上下文、解析目标、保存通道配置版本并加入有界内存队列；不等待实际发送再处理脚本完成消息。
- 上下文从当前行动运行或注入会话获取，不能相信脚本自行传来的脚本/运行身份。
- 发送任务归主进程所有，已接收的通知不因 Worker 正常结束、取消或网站停止而丢弃；强制停止之前尚未被主进程接收的消息不保证发送。
- 参数校验、通道查找、解密、请求、响应解析、日志写入均隔离处理错误，不能触发行动失败、注入停用或编排步骤失败。

### 边界与资源控制
- 全局最多 100 个待发送/发送中投递，最多 4 个并发，同一通道串行；每条网络发送最长 15 秒，排队超过 60 秒则失败，不继续积压。
- Worker 侧限制每个运行/注入作用域每分钟 60 次提交；主进程再次限制每通道每分钟 20 次投递。超额不发送，记录限流原因；连续超额日志按窗口合并计数，避免刷屏和磁盘膨胀。
- 多目标逐个生成投递记录，共用提交 ID；允许部分成功、部分失败，不相互回滚。
- 停用/删除立即阻止新提交及尚未开始的投递；已经发出的请求无法撤回。修改配置只影响后续提交，已有投递保留接收时的配置版本。
- 应用退出先停止脚本及注入生产者，再给通知服务最多 5 秒收尾；未开始的记录标记中断，已发出但未确认的记录标记结果未知，然后释放连接。
- 重启后不恢复发送；残留待发送/发送中记录标记中断或结果未知。异常退出可能丢失尚未落盘的最后几条记录，首版是尽力发送，不承诺可靠送达。
- 不自动重试，也不提供历史一键重发；网络超时可能已经送达，避免产生重复业务通知。

## 五、日志与可观测性
- 状态区分：排队中、发送中、服务端已受理、失败、已跳过、已中断、结果未知。
- 「服务端已受理」不等于用户已收到/已阅读；SMTP 仅代表邮件服务器接受，机器人还须检查平台业务返回码，不能只看 HTTP 200。
- 每条记录包含提交 ID、通道 ID/标识/名称快照、标题、来源、脚本运行/网站/标签 ID、提交及完成时间、耗时、状态、脱敏错误码与原因。
- 不保存正文、凭据、完整请求 URL、原始请求 Header 或原始响应体；标题也可能包含业务信息，界面提示本地日志的隐私边界。
- 保留最近 1,000 条终态投递记录，活动记录不提前淘汰；支持按通道、状态、来源及运行 ID 筛选、分页、查看详情、清空终态日志。
- 脚本日志记录提交 ID，并提供「查看关联通知」入口。最终失败即使发生在脚本结束后也能查到，不异步改写已结束的脚本运行记录。
- 编排任务继续通过现有 `scriptRunId` 关联脚本，不改变其成功/失败判定。
- 日志写入失败时保留有上限的内存记录，并在应用警告区显示问题；日志损坏保留原文件并降级，不静默覆盖，也不拖垮脚本。

## 六、安全、存储与接入现有架构
### 配置与凭据
- 通道元数据放入现有配置的 `notifications` 数组，默认 `[]`，旧配置无需手动迁移。
- 机器人完整 URL、签名密钥、SMTP 配置和凭据、Webhook URL/Header 放入独立加密配置文件，复用现有 Electron `safeStorage` 与 `Encryptor`。常规快照只包含脱敏摘要和是否已配置标记。
- 编辑表单通过专用 IPC 获取非敏感配置；凭据字段显示「已配置」，留空保留，显式替换/清除；新填明文不进入常规状态或持久化明文文件。
- 更新使用「写入新密文 → 原子更新元数据引用」；凭据回收保留当前配置、备份配置及在途投递的引用，避免恢复备份后凭据丢失。
- 钥匙串不可用或解密失败时禁止明文降级，提示重新授权或配置；仅通知功能受影响。

### 网络与权限
- 机器人仅接受各自官方 HTTPS Webhook；通用 Webhook 默认 HTTPS，HTTP 必须用户显式勾选允许不安全连接，可用于本机/内网服务。
- 禁止 URL 内嵌账号密码、非 HTTP(S) 协议和重定向；Header 拒绝换行及 Host/Content-Length 等传输控制字段。响应体有大小上限，错误信息采用安全分类与脱敏处理。
- SMTP 使用 TLS 或强制 STARTTLS并校验证书，不提供忽略证书校验选项。
- 发送使用主进程本机网络，不使用网页 Cookie，也不继承网站的独立代理；首版不新增通知代理配置。
- 脚本仍属于可信本机代码，Worker/vm 不是安全沙箱；授权运行含通知的脚本意味着允许向其指定的已配置通道发送正文。
- MCP 增加只读通道摘要查询与按运行 ID 查询通知日志，并更新 `script_guide`；不开放凭据读取、通道管理或独立直接发送工具。调用脚本沿用现有权限。

## 七、验收与测试
- 渠道：五种适配器的请求格式、签名、SMTP TLS、业务错误码、HTTP 错误、超时、响应体上限、关键词前缀及 UTF-8 内容限制。
- 主流程隔离：通知接口延迟、失败、通道不存在、凭据损坏、日志落盘失败时，行动仍可成功、编排仍进入下一步、注入拦截仍正常工作。
- 生命周期：调用后立即 `return`、取消行动、停止网站、退出应用、异常重启；已接收投递与 Worker 生命周期解耦，不误报发送成功。
- 资源控制：并发、队列满、限流、超额日志合并、多目标部分失败、停用/删除阻止未开始投递、配置编辑不改变已提交内容。
- 安全与兼容：旧配置正常加载；凭据不出现在配置 JSON、备份、快照、MCP 返回或日志；IPC 来源校验、重定向禁止、Header 校验、凭据原子更新和备份恢复。
- Electron E2E：通道增改停用删除、复制示例、测试发送、日志筛选，以及真实行动/注入 Worker 调用链路。网络测试使用本地 HTTP 接收端及模拟 SMTP/平台响应，不向真实用户发送。
- 执行 `npm run typecheck`、`npm run lint`、`npm test`、`npm run test:e2e`，真实平台联调仅在提供测试配置并明确授权后进行。

实施顺序：共享模型与凭据存储 → 发送服务及适配器 → Worker 接入 → 管理界面与日志 → 编辑器/MCP 契约 → 回归验证。本轮仅提交方案，等待确认后修改业务代码。
